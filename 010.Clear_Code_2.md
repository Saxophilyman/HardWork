Уровень классов.

2.1. Класс слишком большой или создаётся слишком много его инстансов  
С этим мы уже сталкивались. В примерах, где намешано много разной и разнородной логики возникае
т много зависимостей друг от друга, код становится громоздким и ломким при изменениях.  
Говоря об инстансах, наверное нужно смотреть на уместность и целесообразность таких случаев.
Каждый объект, особенно сложный будет стоить своих ресурсов и возможно имеет смысл обойтись чем-то другим.
С другой стороны даже не представляю, чем можно обойтись в случае создания GPS-point

Пример:

```java
public class DataGenService {
    public void generate(DataGenDTO request) {
    }

    private List<Vehicle> generateVehicles(...) {
    }

    private List<Driver> generateDrivers(...) {
    }

    private Brand genBrandOwner(...) {
    }

    private String generateVehicleName(...) {
    }

    private int generateVehicleCost() {
    }

    private int generateVehicleYearOfRelease() {
    }

    private void assignVehicleWithDriver(...) {
    }
}
```

Удобный для меня класс, который одним махом делает сразу всё. Вся логика и все операции прописаны
в методах. Если же исходить из более долгосрочных перспектив, то я хотя бы разбил сервис на логические
блоки и вынес их в отдельные классы, а сервис бы использовал как вызов методов по сценарию.

```java
public class VehicleDataFactory {
    public List<Vehicle> createVehicles(Enterprise enterprise, int count) {
        // логика создания машин
    }
}
```

--

Пример с инстансом:

```java
for(User user :users){
PasswordValidator validator = new PasswordValidator();
    validator.

validate(user.getPassword());
        }
```

Вместо того, чтобы его создавать каждый раз - достаточно одного. А в дальнейшем переиспользовать.

```java
PasswordValidator validator = new PasswordValidator();

for(
User user :users){
        validator.

validate(user.getPassword());
        }
```

Либо попробовать использовать Spring-bean

2.2. Класс слишком маленький или делает слишком мало.  
Этот пункт снова наводит меня на мысль, что думать нужно не столько о коде, сколько о его смысловых единицах.
Бывает, что сам по себе маленький класс это совершенно не плохо, если он оформляет определённое смысловое значение.
Но бывает архитектура ради архитектуры, когда маленький класс является избыточным
или по своему значению почти ничего не делает.  
Думаю даже в вышеприведённом примере с сервисом генерации,
если его просто разбивать на много мелких частей-классов, которые выполняют только один вызов,
это относилось бы к данному случаю.

```java
public class VehicleDataFactory {
    public List<Vehicle> createVehicles(Enterprise enterprise, int count) {
        return enterprise.createVehicle(count);
    }
}
```

Но уже другим был момент, если бы он содержал собственные правила генерации или инварианты.

2.3. В классе есть метод, который выглядит более подходящим для другого класса.
Мне кажется, что здесь включается ещё больше "нюансовости", в которой не так-то просто отличить одно от другого
Возможно здесь стоит больше внимания обращать на методы, где используются данные другого класса
или относятся к другой ответственности и учиться смотреть что где за что отвечает.

В более же классическом случае я бы представил подобный пример:

```java
public class Vehicle {

    private String licensePlate;
    private String brand;

    public String toCsvRow() {
        return licensePlate + "," + brand;
    }
}
```

подходящий для другого класса:

```java
public class VehicleCsvExporter {

    public String toCsvRow(Vehicle vehicle) {
        return vehicle.getLicensePlate() + "," + vehicle.getBrand();
    }
}
```

2.4. Класс хранит данные, которые загоняются в него в множестве разных мест в программе.  
Очень частый случай в моей практике.
Проблемой является как то, что объект долго живёт в промежуточном, так и возможное невалидное состояние.
Сам разброс, и связанные с ним сложности контроля. Да и другие моменты.   
Только впоследствии приходишь к применению record или builder.  
Впрочем, иногда без последовательного заполнения сложно обойтись, особенно в случае с JPA-сущностями
и здесь имеет смысл иметь централизованное место или класс для этого, например, используя фабрику или маппер.  
Упрощённый некорректный пример:

```java
public class ReportRequest {

    private String vehicleNumber;
    private LocalDate startDate;
    private LocalDate endDate;
    private String format;
    private boolean includeGps;

    public void setVehicleNumber(String vehicleNumber) {
        this.vehicleNumber = vehicleNumber;
    }

    public void setStartDate(LocalDate startDate) {
        this.startDate = startDate;
    }

    public void setEndDate(LocalDate endDate) {
        this.endDate = endDate;
    }

    public void setFormat(String format) {
        this.format = format;
    }

    public void setIncludeGps(boolean includeGps) {
        this.includeGps = includeGps;
    }
}
```

```java
ReportRequest request = new ReportRequest();

controller.

fillVehicleNumber(request);
dateService.

fillPeriod(request);
exportController.

fillFormat(request);
uiService.

fillGpsFlag(request);

reportService.

build(request);
```

И более лучший способ - использовать билдер

```java
ReportRequest request = new ReportRequest.Builder()
        .vehicleNumber(vehicleNumber)
        .startDate(startDate)
        .endDate(endDate)
        .format("CSV")
        .includeGps(true)
        .build();

reportService.

build(request);
```

2.5. Класс зависит от деталей реализации других классов.  
Тоже вопрос, который часто разбирался в примерах со связанностью
и его последствиях в случае изменения кода в одном месте. Но размышляя над ним и изучая примеры,
у меня возникла одна мысль, не знаю насколько она достоверно правильная. Ключевым моментом
является ситуация, когда один класс знает детали реализации другого класса.
И в учебном случае можно было бы указать следующий условный пример:

```java
public class ReportService {
    public void build(UserRepository repository) {
        repository.getEntityManager()
                .createNativeQuery("SELECT * FROM users");
    }
}
```

В котором сервис как бы знает о том, что имеется в реализации репозитория.
Строя более правильную версию мы разделяем подобную связку через обращение к публичному методу,
в котором не важно как необходимое нам реализовано.

```java
public class UserRepository {

    public List<User> findAllUsers() {
        return entityManager
                .createQuery("SELECT u FROM User u", User.class)
                .getResultList();
    }
}
```

```java
public class ReportService {
    private final UserRepository userRepository;

    public ReportService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    public Report build() {
        List<User> users = userRepository.findAllUsers();
        return new Report(users);
    }
}
```

Но если размышлять в подобном ключе, то получится, что в большинстве моих случаев,
как минимум в контроллерах, именно такой "некорректный" вариант и прослеживается.
А ведь это считалось даже нормой для меня.
К примеру вызовы рода
vehicle.getEnterpriseOwnerOfVehicle().getEnterpriseId();  
dto.getBrand().getBrandId();  
driver.getEnterpriseOwnerOfDriver().getEnterpriseId()  
И так во множестве мест. Значит ли это, что мы должны отвязывать подобные случаи от обращения к внутренней реализации?
Думаю, что да. Особенно, если это используется в проекте не единожды.

В общем на учебных примерах всё выглядит гораздо понятнее))

2.6. Приведение типов вниз по иерархии.  
Насколько помню это ситуация связанная с преимуществом использования полиморфизма.
Теперь же можно использовать и паттерн Visitor.
В случае же приведения типов, мы попадаем в ловушку расширения при добавлении нового типа.
Например:

```java
public abstract class Report {
}
```

```java
public class VehicleMileageReport extends Report {

    private final int mileage;

    public VehicleMileageReport(int mileage) {
        this.mileage = mileage;
    }

    public int getMileage() {
        return mileage;
    }
}
```

```java
public class FuelReport extends Report {

    private final int fuel;

    public FuelReport(int fuel) {
        this.fuel = fuel;
    }

    public int getFuel() {
        return fuel;
    }
}
```

```java
public class ReportPrinter {

    public void print(Report report) {

        if (report instanceof VehicleMileageReport mileageReport) {
            System.out.println(
                    "Mileage report: " + mileageReport.getMileage()
            );

        } else if (report instanceof FuelReport fuelReport) {
            System.out.println(
                    "Fuel report: " + fuelReport.getFuel()
            );

        } else {
            throw new IllegalArgumentException("Unknown report type");
        }
    }
}
```

```java
public class Main {
    public static void main(String[] args) {
        Report report = new VehicleMileageReport(1200);
        ReportPrinter printer = new ReportPrinter();
        printer.print(report);
    }
}
```

Используя полиморфизм - мы отвязываемся от проверки каждого типа.

```java
public interface Report {
    void print();
}
```

```java
public class VehicleMileageReport implements Report {

    @Override
    public void print() {
        System.out.println("Mileage report");
    }
}
```

```java
public class FuelReport implements Report {

    @Override
    public void print() {
        System.out.println("Fuel report");
    }
}
```

```java
public class Main {
    public static void main(String[] args) {
        Report report1 = new VehicleMileageReport(1200);
        Report report2 = new FuelReport(200);

        report1.print();
        report2.print();
    }
}
```

2.7. Когда создаётся класс-наследник для какого-то класса,
приходится создавать классы-наследники и для некоторых других классов.  
Очень интересный пункт, до проблемы которого не всегда можно дойти на учебных примерах и даже
на учебных проектах. Естественно расширяя систему классов нет ничего сложного в том, чтобы добавить
ещё несколько классов-наследников и создать ещё несколько в других.
Но что если добавляются или планируется добавить несколько десятков?
Ответ на данный вопрос беспокоил меня ещё пару лет назад. Отчёты, форматы и так далее,
являлись наиболее показательными для данной проблемы.  
Наверное здесь проще будет объяснить себе словами, чем кодом.
```java
/*
Допустим есть тип Report.  
  Для него есть наследники:  
  MileageReport  
  FuelReport
    Логично сделать:
    MileageReportPrinter 
    FuelReportPrinter
            
    Продолжить с:
    MileageReportExporter
    FuelReportExporter

Но при добавлении TemperatureReport 
придётся также добавить:
TemperatureReportPrinter
TemperatureReportExporter

а теперь добавим ещё 10 типов ***Report
 */
```
Но подобная проблема может возникать не только при наследниках. 
И тут главное правильно организовать структуру для последующего расширения. 
Использовать полиморфизм, композицию, паттерны, приёмы для "оркестрации".
И насколько понимаю универсального решения здесь нет и нужно отталкиваться от задач и контекста.

2.8. Дочерние классы не используют методы и атрибуты родительских классов, 
или переопределяют родительские методы.  
Не могу отделаться от мысли, что сейчас редко встретишь крупные выстроенные иерархии классов,
в большем случае используются другие приёмы. Говоря же о самом пункте, пожалуй, подобное
мы проходили в примерах неистинного наследования, а также отчасти здесь будет подходящим
принцип подстановки Барбары Лисков.  
Пусть в данном случае будет приведён классический некорректный пример
```java
abstract class Bird {
    abstract void fly();
}
```
```java
class Eagle extends Bird {
    @Override
    void fly() {
        System.out.println("Flying");
    }
}
```
```java
class Penguin extends Bird {
    @Override
    void fly() {
        //не умеют летать...
    }
}
```

Уровень приложения.

3.1. Одна модификация требует внесения изменений в несколько классов.  
Кажется это мне гораздо ближе и с этим я сталкиваюсь постоянно.
В проекте автопарк похожее встречалось в модуле отчётов. Особенно по началу.
При добавлении нового типа отчёта или новой его фишки потенциально приходилось вносить изменения 
в enum ReportType, контроллер, список типов отчётов, switch-блока, HTML-шаблона,
сервиса расчёта и возможно где-то ещё.

Приходилось большее внимание уделять модульности и самостоятельности каждого класса, 
и организовывать их взаимодействие через композицию, "обработчики" или более абстрактные интерфейсы.

3.2. Использование сложных паттернов проектирования там, 
где можно использовать более простой и незамысловатый дизайн.

Слишком я неискушён в сложных паттернах и их реальном постоянным применением.  
Однако сталкивался с желанием строить архитектуру ради архитектуры или 
попытки сразу заложить в приложение возможные последующие изменения и расширения,

На более простом уровне сталкивался с попыткой вынести в отдельные классы логику из основного класса,
хотя она использовалась единожды и можно её было оставить без изменений.

Как мне кажется, некоторые "запахи" можно даже принять за антагонистов друг друга и не различить их особенности.
