Не до конца могу провести грани, но насколько понимаю, помимо основного совета вообще не пользоваться по возможности изменяемыми состояниями, суть заключается в определении смысла данных и более эффективном их использовании на основании того же смысла. Если говорить о передаче по ссылке, то разные части программы при её использовании начинают работать с одним и тем же объектом, а это накладывает сопутствующие этому зависимости, совместную используемость, хрупкость, сложность и т.д. Вполне возможно, что для того, кто использует, вся сущность не требуется и вполне можно обойтись определённым набором данных, которые можно выразить через иммутабельное состояние. 
Говоря о java, технически можно воспользоваться record или неизменяемым классом.
Только вот непросто перейти с обычного отношения к объекту и сущности на уровень смысла. Более прост подход в отношении количества полей и необходимых полей для передачи. И подобные приёмы уже использовались в предыдущих рефакторингах.

№1.  
Касаемо первого примера аналогичный подход уже используется в более новой части проекта trackingRef, там автомобиль передаётся через иммутабельный VehicleRef, период и телеметрия представлены также отдельными неизменяемыми состояниями.  
В TripImportHelper в генерации и сохранении трека используется Vehicle, затем данные передаются в GpsTrackService
```java
public Instant generateAndSaveTrack( 
      List<GeoPoint> track,
      Instant startTime,
      Vehicle vehicle,
      Duration pointInterval )
```
И мы получаем для этой операции ссылку на сущность и все её поля/состояния целиком. Это также может соответствовать предыдущим темам HardWork, где условный контракт разрешает больше, чем требуется. 
Но для данного метода нужна не сама сущность, а по сути его идентификатор, чтобы связать точки с конкретным автомобилем gpsPoint.setVehicleIdForGps(vehicle);

вместо этого можно передавать сам идентификатор в иммутабельном виде, который уже имеется и используется в отрефакторенной части проекта
`public record VehicleRef(Long id) { }`

тогда получится почти то же 
```java
public Instant generateAndSaveTrack( 
      List<GeoPoint> track,
      Instant startTime,
      VehicleRef vehicle,
      Duration pointInterval)
```
Но передаваться уже будет не полный объект, а его иммутабельное значение.

В месте сохранения через репозиторий всё равно нужно будет передать сущность, но это будет уже другая граница.  
И изменяемая сущность появится там, где она непосредственно должна использоваться.

№2  
Снова абстрагируясь от возможных более крупных изменениях и концентрируясь на конкретном задании.
В сервисе имеется код для обновления данных vehicle
```java
public void update(
        Long id,
        Vehicle updatedVehicle,
        Long updatedBrandId,
        Long enterpriseId
) {
    Vehicle existing = findVehicleOrThrow(id);

    validateLicensePlateForUpdate(id, existing, updatedVehicle);
    applyEditableFields(existing, updatedVehicle);

    //...
}
```
в нём участвует как сам Vehicle, который мы получаем в existing и данные для обновления updatedVehicle, тоже как сам Vehicle.
Если говорить о смысле данных, то existing является объектом, который мы хотим изменить. 
А updatedVehicle является данными формы, которую может заполнить пользователь для изменения существующего(existing) Vehicle. Но по факту принимается новый Vehicle, значения из которого копируются в имеющийся в БД existing Vehicle. К тому же после сбора данных в форме updatedVehicle также проходит и через контроллер.

можно также использовать неизменяемый набор нужных данных, при этом обозначить только те, которые нам действительно нужны
```java
public record VehicleUpdateState(
        String vehicleName,
        String licensePlate,
        int vehicleCost,
        int vehicleYearOfRelease,
        Long brandId
) {}
```

`VehicleUpdateState state = new VehicleUpdateState(
///...
)`

```java

public void update(
        Long vehicleId,
        VehicleUpdateState state,
        Long enterpriseId
)
```
а внутри при назначении новых полей
```java
Vehicle existing = findVehicleOrThrow(vehicleId);

existing.setVehicleName(state.vehicleName());
existing.setLicensePlate(state.licensePlate());
existing.setVehicleCost(state.vehicleCost());
```
Это будет более явно отражать смысл и применение данных в данном методе.
Контроллер и сервис не разделяют изменяемый Vehicle, update не зависит от всего Vehicle и предоставляет только необходимые поля.

и снова
```java
@GetMapping("managers/report/view")
public String viewReport(
        @CurrentManagerId Long managerId,
        Model model,
        HttpSession session
) {
    ModelReport report = (ModelReport) session.getAttribute("report");

    Vehicle vehicle = (Vehicle) session.getAttribute("vehicle");

    if (report == null) {
        return "/report/vehiclesReport";
    }

    model.addAttribute("report", report);
    model.addAttribute("vehicle", vehicle);

    session.removeAttribute("report");
    session.removeAttribute("vehicle");

    return "/report/viewReport";
}
```
Получается, что vehicle как изменяемая сущность гоняется по всему пути. Сервису же нужны от vehicle только данные предприятия и транспортного средства по id. А шаблону по html нужны только vehicleId, enterpriseId и licensePlate.
