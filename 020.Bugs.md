Но если смотреть шире, как в материале, всё становится ясно. И даже на моей маленькой практике обучения и разработке проекта возникало не мало описываемых типов "багов". Другое дело, что все они так похожи друг на друга, что ещё стоит постараться отличить и классифицировать один от другого.

### 1. Это не баг.
Хотя выглядит странно.

№1  
В предыдущих занятиях при рефакторинге была создана модель события VehicleDomainEvent, которая содержит следующие данные
```java
public record VehicleDomainEvent(
        UUID vehicleGuid,
        UUID enterpriseGuid,
        Long managerId,
        Action action,
        String licensePlate,
        String vehicleName,
        String enterpriseName
) {
```
при этом был оставлен предыдущий вариант конструктора для старых вызовов
```java
public VehicleDomainEvent(
        UUID vehicleGuid,
        UUID enterpriseGuid,
        Long managerId,
        Action action
) {
    this(
            vehicleGuid,
            enterpriseGuid,
            managerId,
            action,
            null,
            null,
            null
    );
}
```
Он не даёт ошибки, хотя может выглядеть странно с учётом использования null для полей, но старые вызовы работают и используют его. По сути старый вариант остался в качестве переходной модели к новому варианту. Но как долго он может им оставаться? Иногда навсегда.

№2  
В проекте имеется DevGrafanaSmokeTestController, предназначенный для проверки работы мониторинга. Контроллер включается при наличии настройки для этого. В нём определены специальные endpoint'ы, которые специально создают ситуации, обычно воспринимаемые как ошибки(HTTP 400, 500, медленный запрос). Если бы это было вне контекста цели их использования, то они являлись багом. Но они созданы специально для тестов и проверки поведения под эти ошибки.

### 2. Это не баг (а что-то другое)
Но очень хочется назвать багом))

№1  
Оставил сам себе подсказку под данный пример)) 
Существует ли пользователь с данным именем через проверку в исключении
```java
@Override
public void validate(Object target, Errors errors) {
    //впоследствии реализовать новый класс(сервис) возвращающий Optional

    Manager manager = (Manager) target;

    try {
        generalDetailsService.loadUserByUsername(
                manager.getUsername()
        );
    } catch (UsernameNotFoundException ignored) {
        return;
    }

    errors.rejectValue(
            "username",
            "менеджер с таким именем уже существует"
    );
}
```
```java
public UserDetails loadUserByUsername(String username)
        throws UsernameNotFoundException {

    Optional<Manager> manager =
            managerRepository.findByUsername(username);

    if (manager.isPresent()) {
        return new ManagerDetails(manager.get());
    }

    Optional<SimpleUser> user =
            simpleUserRepository.findByUsername(username);

    if (user.isPresent()) {
        return new SimpleUserDetails(user.get());
    }

    throw new UsernameNotFoundException(
            "User not found with username: " + username
    );
}
```
Результат вроде бы корректен, но сейчас более ясно то, что реализация корявая. Особенно использование исключения в качестве механизма управления потоком. Это и тех. долг, но слишком кричаще.

№2  
Без лишнего кода, имеется логика создания пагинации с сортировкой. При этом сама реализация присутствует в 2х местах, в UI и Rest, и используется в двух местах соответственно. И по сути они выдают одинаковый результат. Это явный кандидат на рефакторинг, не баг и всё работает, но это почти дублирование кода. А если мыслить на будущее - возможный кандидат к типу бага №4 про хрупкость при возможном изменении логики реализации.


### 3. Это сбивает людей с толку
Можно много привести случаев под этот пример, многие задания мы делали для избегания этого. 

№1  
Самый простой случай с наименованиями, когда тебе понятно, а для других возможно уже нет.
Допустим в сущности есть поле `private Vehicle vehicleIdForGps`. Типом является Vehicle, а название vehicleIdForGps и сторонний человек в вызове метода, не разобравшись, может подумать что мы обращаемся к самому id, где типу естественнее быть long или uuid. На деле же всё работает и вызов можно осуществить через `g.vehicleIdForGps.vehicleId`. Но путаница может возникнуть

№2  
То же, что разбирали по смыслу данных, когда мы обращаемся к полноценному объекту, а проще и понятнее использовать его представление в необходимом нам виде, потому что это отражает явное его значение. С предыдущим примером Vehicle existing и Vehicle updatedVehicle, где без разбора, можно сделать вывод, что мы работаем с двумя сущностями, хотя используется только одна, а вторая работает как набор данных для изменения/обновления полей 


### 4. Это хрупкость
Со временем намерена испортить поведение

№1  
Также встречался с подобным, один из явных, ярких случаев, когда в своё время была использована аннотация @Max(value = 2024) для создания автомобилей. На тот момент это работало, сейчас же это уже стало не корректным и не соответствующим "реальности". В действительности суть этого ограничения мог соответствовать условию год автомобиля не должен быть больше текущего года. Но реализован был с латентной ошибкой. 

№2  
Со вторым примером несколько сложнее. Возможно подойдёт ситуация с которой сталкивался при развёртывании приложения. У меня было несколько профилей для "запуска". а порты типа 8080 захардкожены и запуск осуществлялся на них. Когда я запускал локально тестовые случаи спокойно отрабатывали. Но когда пытался разворачивать условно "в прод", мои тесты падали, а приложение не развёртывалось. Приходилось долго искать проблему, а она как раз и заключалась в жестко прописанный портах.
